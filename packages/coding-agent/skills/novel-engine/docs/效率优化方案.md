## 二、瓶颈分析

### 瓶颈1：串行调用（最大瓶颈，可提速 2-3x）

**问题**: 整个 pipeline 是严格串行的——每个阶段必须等上一个完成。但同一章内的某些调用不依赖彼此输出：

```
当前（串行，~160s）:
Director → Synopsis → Scene1 → Scene2 → Scene3 → Scene4 → Polish → Review

实际依赖图:
  Director (需要 plot_graph, bible, world_state)
    ├── Synopsis (需要 Director output)
    │     ├── Scene1 (需要 Synopsis output)
    │     ├── Scene2 (需要 Synopsis output)
    │     ├── Scene3 (需要 Synopsis output)
    │     └── Scene4 (需要 Synopsis output)
    ├── Polish (需要 all scenes combined)
    └── Review (需要 polished chapter)
```

**关键发现**: Scene1-4 之间**无依赖**！它们都只依赖 Synopsis 的输出，但彼此独立。

### 瓶颈2：重复加载 bible 文件（可节省 10-20% token）

**问题**: `ChapterDirector.get_context_for_chapter()` 每次调用都从磁盘读取全部 bible 文件并拼入 prompt。这些文件对每章都是不变的。

- `world_bible.md` (~2KB) → 截断到 2000 chars
- `character_bible.md` (~2.2KB) → 截断到 1500 chars
- `style_bible.md` (~1.1KB) → 截断到 1000 chars
- `author_intent.md` (~2.3KB) → 截断到 2000 chars

每次截断都丢失信息，且每次都重新发送相同内容。

### 瓶颈3：recent_summaries 增长导致 prompt 膨胀（长期瓶颈）

**问题**: `get_context_for_chapter()` 加载 `count=20` 的 recent_summaries。每章 ~250-500 chars summary，20章 = 5-10KB。随着章节增加，prompt 越来越大。

Ch1: 45K tokens → Ch5: 189K tokens → Ch100+: 可能超过 300K tokens/call

### 瓶颈4：Fix Loop Bug（质量缺陷）

**严重 BUG**: `pipeline/pipeline_orchestrator.py` 第 164-170 行的 fix loop 有致命错误：

```python
# 当前代码（BUG）:
elif verdict == "fix":
    fix_prompt = self.reviewer.generate_fix_prompt(review, novel_text)  # 生成但未使用！
    fixed_text = self.writer.polish_chapter(novel_text, task_card)       # 调用的是通用润色，不是修复！
    self.current_novel = fixed_text
```

**问题**: `generate_fix_prompt()` 的结果被丢弃，`polish_chapter()` 用的是通用润色 prompt，不包含审查意见中的具体问题描述。这意味着 fix loop **实际上没有做任何针对性修复**。

**影响**:
- 30% 触发 fix loop 的章节，修复成功率极低
- 解释了为什么有些章节分数低但仍能通过（靠的是运气而非修复机制）

## 三、优化方案（按 ROI 排序）

### P0：修复 Fix Loop Bug（零成本，立即提升质量）

**实现**: 在 `pipeline/pipeline_orchestrator.py` 第 164-170 行：

```python
elif verdict == "fix":
    # 使用审查意见生成针对性修复 prompt
    fix_prompt = self.reviewer.generate_fix_prompt(review, novel_text)
    # 用修复 prompt 调用 LLM 生成修复后文本
    from llm_client import call_llm
    fixed_text = call_llm(
        prompt=fix_prompt,
        system_prompt=self.writer.SCENE_SYSTEM_PROMPT,
        client=self.writer.llm,
    )
    self.current_novel = fixed_text
    result["errors"].append(f"FIX: score={score}")
```

**预期效果**: Fix loop 真正有效，减少全量重试（retry），节省 10-15% token。

**实现难度**: ⭐（极低，3 行代码改动）

### P0：Scene 并行化（最高 ROI，提速 25-50%）

**原理**: Scene1-4 彼此独立，可并发调用 LLM API。

**实现**: 修改 `agents/writer_agent.py` 的 `generate_full_chapter()`：

```python
import asyncio

async def _generate_scene_async(self, task_card, synopsis, scene_bp):
    """异步生成单个场景"""
    return self.generate_scene(task_card, scene_bp, synopsis)

def generate_full_chapter(self, task_card, synopsis):
    """并行生成所有场景"""
    scenes = task_card.get("scene_blueprints", [])

    async def _parallel_generate():
        tasks = [
            asyncio.create_task(
                self._generate_scene_async(task_card, synopsis, bp)
            )
            for bp in scenes
        ]
        return await asyncio.gather(*tasks)

    scene_contents = asyncio.run(_parallel_generate())

    full_chapter_parts = []
    for i, (content, bp) in enumerate(zip(scene_contents, scenes)):
        scene_num = bp.get('scene_num', i+1)
        location = bp.get('location', '')
        full_chapter_parts.append(
            f"【场景{scene_num}：{location}】\n\n{content}\n\n※\n"
        )

    full_chapter = "\n".join(full_chapter_parts)

    hook = task_card.get("chapter_hook", "")
    if hook:
        full_chapter += f"\n\n---\n*（章末钩子：{hook}）*"

    logger.info(f"Full chapter generated ({len(full_chapter)} chars)")
    return full_chapter
```

**预期效果**:
- Scene 部分从 ~40s 降到 ~10s（4 scenes 并发）
- 总耗时从 ~160s 降到 ~120s（约 25% 提升）
- 如果配合 Director 也并行化（Director 和 Synopsis 无依赖），可进一步降到 ~90s

**风险**:
- API 限流（SiliconFlow API 是否有 rate limit？）
- Token 并发限制（需确认）
- 修改量中等（需改造 agents/writer_agent.py）

**实现难度**: ⭐⭐⭐（中等）

### P1：Bible 上下文压缩（省 token 15-20%）

**原理**: Bible 文件每次都被完整加载+截断。改为：
1. **缓存 bible hash** — 不变时不重新发送
2. **system prompt 注入** — 把 bible 内容放在 system message 而非 user prompt
3. **按需引用** — 只在相关阶段发送对应 bible

**实现**:

```python
# Option A: System prompt injection (API 支持 system role)
SYSTEM_PROMPT = """你是小说生成流水线。以下是世界观设定（不会改变）：
{world_bible}
以下是人物设定：
{character_bible}
..."""

# Option B: Bible hash cache
self._bible_cache = {}
def _load_bible_cached(self):
    files = {
        'world': 'bible/world_bible.md',
        'character': 'bible/character_bible.md',
        ...
    }
    for name, path in files.items():
        full_path = self.root / path
        if not full_path.exists(): continue
        h = hashlib.sha256(full_path.read_bytes()).hexdigest()[:8]
        current = {'hash': h, 'text': full_path.read_text()}
        if name in self._bible_cache and self._bible_cache[name]['hash'] == h:
            # Bible didn't change, reuse cached version
            pass
        self._bible_cache[name] = current
```

**预期效果**:
- System prompt 中的 bible 不计入 user prompt token 成本（如果 API 区分 system/completion tokens）
- 即使不区分，减少 prompt 冗余也能降低 token 用量
- 节省 15-20% token 成本

**风险**:
- 取决于 API 是否区分 system/completion token 定价
- 修改量小

**实现难度**: ⭐⭐（低）

### P1：Fix Prompt 优化（配合 P0 修复）

**问题**: Fix prompt 包含完整的原始章节文本（6000 chars），然后让 LLM "只修改问题段落"。这导致：
1. 大量 token 浪费在复制原文上
2. LLM 经常误删未标记的段落

**方案**: 改为**增量修复**模式：

```python
def generate_fix_prompt(self, review, novel_text):
    issues = review.get('issues', [])

    # 只提取问题段落（不是全文）
    problem_segments = []
    for issue in issues:
        fix_scope = issue.get('fix_scope', '')
        if fix_scope:
            # 从原文中提取指定段落
            segment = self._extract_segment(novel_text, fix_scope)
            problem_segments.append({
                'issue': issue['description'],
                'suggested_fix': issue['suggested_fix'],
                'original_text': segment[:2000],  # 只发问题段落
            })

    return f"""请根据以下审查意见修复章节。
只修改指定的问题段落，不要改动其他内容。

## 修复清单
{json.dumps(problem_segments, ensure_ascii=False, indent=2)}

## 要求
1. 输出完整的修复后章节
2. 只修改问题段落，其余保持原样"""
```

**预期效果**:
- Fix prompt token 从 ~6K 降到 ~2K
- LLM 更精准地修改，减少误删
- 预计 fix loop 成功率提升 10-15%

**风险**:
- 需要实现 `_extract_segment()` 来定位段落
- 段落定位可能不准确

**实现难度**: ⭐⭐（低）

### P2：滑动窗口摘要替换（解决长期膨胀）

**问题**: `recent_summaries` 加载 20 章摘要，每章增长都增加 token 用量。

**方案**: 维护一个**固定大小的剧情摘要**（非原文摘要，而是压缩后的剧情状态）：

```python
class PlotSummaryCache:
    """维护固定大小的剧情摘要，替代 raw chapter summaries"""

    def __init__(self, project_root):
        self.summary_file = Path(project_root) / "memory" / "plot_summary.json"
        self.max_entries = 10  # 最多保留 10 个剧情块

    def add_chapter_summary(self, chapter_num, summary):
        """添加章节摘要，合并到现有剧情块"""
        data = self._load()

        # 找到最近的剧情块（5章窗口）
        merged = False
        for entry in data['blocks']:
            if abs(entry['chapter_range'][1] - chapter_num) <= 5:
                entry['summary'] += '\n' + summary
                entry['chapter_range'][1] = chapter_num
                merged = True
                break

        if not merged:
            data['blocks'].append({
                'chapter_range': [chapter_num, chapter_num],
                'summary': summary
            })

        # 保持固定大小
        while len(data['blocks']) > self.max_entries:
            data['blocks'].pop(0)

        self._save(data)

    def get_context(self, chapter_num):
        """获取剧情上下文（固定大小，不随章节增长）"""
        data = self._load()
        return data['blocks'][-self.max_entries:]
```

**预期效果**:
- Prompt 大小不再随章节增长
- 固定 ~10 个剧情块 × ~500 chars = ~5KB 恒定开销
- 相比当前的 20 章 × ~500 chars = ~10KB，节省 50%

**风险**:
- 剧情块合并可能丢失细节
- 需要设计合理的合并策略

**实现难度**: ⭐⭐⭐（中等，需新增模块）

### P2：预计算 Director 输入缓存（省 I/O 5-10%）

**原理**: Director 的 `get_context_for_chapter()` 加载大量数据，其中大部分（bible, volumes, plot_graph）每章不变。只有 `constraints` 和 `foreshadows` 随章节变化。

**实现**: 在 `PipelineOrchestrator.__init__()` 中预计算 Director 的固定上下文：

```python
class PipelineOrchestrator:
    def __init__(self, project_root):
        self.director_cache = {
            'bible': director._load_all_bible(),  # 一次性加载
            'volumes': volumes,
            'plot_graph': plot_graph,
            'foreshadow_registry': foreshadow_registry,
        }

    def generate_single_chapter(self, chapter_num):
        # Director 使用缓存 + 动态部分
        dynamic_context = {
            'constraints': simulator.get_constraints_summary(chapter_num),
            'world_state': simulator.build_world_state_for_chapter(chapter_num),
            'recent_summaries': memory.get_recent_summaries(chapter_num),
        }
        task_card = director.generate_task_card_cached(chapter_num, dynamic_context)
```

**预期效果**:
- 减少每章的 I/O 开销
- Bible 文件只读一次（项目初始化时）
- 预计节省 5-10% 每章处理时间

**风险**:
- 内存占用增加（存储 bible + plot_graph）
- 修改量小

**实现难度**: ⭐⭐（低）

### P3：批量场景生成（实验性，可能省 token 30%）

**原理**: 与其生成 4 个独立场景再拼接，不如让 LLM **一次生成整章**。

**实现**:

```python
def generate_full_chapter_batch(self, task_card, synopsis):
    """单次调用生成整章，而非分场景"""
    prompt = f"""基于以下任务卡和缩写，生成完整章节。

## 场景蓝图
{json.dumps(task_card['scene_blueprints'], ensure_ascii=False, indent=2)}

## 要求
按照场景蓝图生成完整章节，确保：
1. 每个场景的 goal/conflict/emotion 都得到体现
2. 场景间过渡自然
3. 总字数 4000-5000 字"""

    return call_llm(prompt, system_prompt=self.SCENE_SYSTEM_PROMPT)
```

**预期效果**:
- 从 4 scene calls + 1 polish call = 5 calls → 1 call
- 减少上下文切换，质量可能更高
- 但 completion token 需求大增（可能超出 max_tokens）

**风险**:
- 单章可能超出 max_tokens=16384（thinking + content）
- 长文本质量可能下降
- 需要测试验证

**实现难度**: ⭐⭐⭐⭐（高，需大幅重写 writer_agent）
