# 小说生成流水线 — 人工编写指南

> 本文档说明流水线运行所需的所有人工输入文件。每个文件都对应流水线中的一个特定模块，LLM 会在生成章节时读取它们作为约束和上下文。

---

## 总览：文件位置与用途

```
src/novel_engine/
├── bible/                          # 世界观与创作圣经（永不改变）
│   ├── world_bible.md              # 世界观设定
│   ├── character_bible.md          # 人物档案
│   ├── style_bible.md              # 文风规则
│   ├── author_intent.md            # 创作意图与分阶段约束
│   └── ending_bible.md             # 终局设定与命运锚点
├── planning/                       # 剧情规划（可迭代更新）
│   ├── volumes.json                # 卷纲
│   └── plot_graph.json             # 剧情DAG
├── simulation/                     # 规则引擎（通常不需要改）
│   ├── rules.json                  # 世界运行规则
│   └── constraints.json            # 角色境界锁定
├── foreshadow/                     # 伏笔管理
│   └── registry.json               # 伏笔注册表
├── config/                         # 流水线配置（已预设，通常不需要改）
│   ├── quality_thresholds.json     # 评分标准
│   └── runtime_config.json         # API密钥与运行时参数
└── memory/world_state/             # 运行时状态（自动生成，不要手动编辑）
    ├── characters.json             # 角色当前状态
    └── power_system.json           # 突破历史
```

---

## 1. `bible/world_bible.md` — 世界观设定

**作用**: 为 LLM 提供故事发生的世界的基本规则。LLM 在生成任务卡时会截取前 2000 字符。

**必须包含的部分**:

### 时代背景 (1-2段)
用简洁的语言描述故事发生的时代、文明水平、核心矛盾。

```markdown
## 时代背景
[描述世界的整体氛围、文明阶段、核心冲突]
```

### 地理格局
列出所有会涉及的主要地点，每个地点一句话描述其特征。

```markdown
## 地理格局
- **地点名** — 一句话特征描述
- **地点名** — 一句话特征描述
```

> **注意**: 只列出前 800 章内会出现的地点。后续新地点可以在 `planning/volumes.json` 中新增卷时补充。

### 势力分布
列出所有主要势力及其特点。

```markdown
## 势力分布
### 势力类别（如"九大宗门"）
1. **势力名** — 一句话定位
2. **势力名** — 一句话定位

### 皇朝/组织名
- **名称**：一句话描述

### 其他群体
- **名称**：一句话描述
```

### 力量体系
用表格列出所有修炼境界及其关键信息。

```markdown
## 力量体系（修炼境界）
| 境界 | 寿元 | 说明 |
|------|------|------|
| 炼气期 | 150年 | 初入修真，感应灵气 |
| ... | ... | ... |
```

> **重要**: 境界名称和顺序一旦确定，后续不要更改。`simulation/constraints.json` 中的 `realm_lock` 依赖这些名称。

### 关键规则
列出 3-10 条世界运行的铁律。

```markdown
## 关键规则
1. [规则一]
2. [规则二]
...
```

**编写原则**:
- 控制在 2KB 以内（LLM 截取 2000 字符）
- 只写**事实性设定**，不写具体剧情
- 语言简洁，每条一行
- 如果超过 2000 字符，优先保留"地理格局"和"力量体系"

## 2. `bible/character_bible.md` — 人物档案

**作用**: 定义所有角色的性格、关系、成长弧光。LLM 在生成任务卡时截取前 1500 字符。

**必须包含的部分**:

### 核心人物
每个人物一个条目，格式如下：

```markdown
## 核心人物

### C001 姓名（角色定位）
- **身份**：[社会身份、出身]
- **性格**：[3-5个性格关键词+简短解释]
- **初始境界**：[修炼境界]
- **金手指/特殊能力**：[如有]
- **成长弧光**：[从什么状态 → 到什么状态]
- **口头禅/习惯**：[标志性行为]
- **禁忌**：[绝对不能做的事]
```

> **ID命名规范**: C001, C002, ... C999。ID 会在 `plot_graph.json` 和 `constraints.json` 中被引用。

### 人物关系矩阵
列出所有重要关系对：

```markdown
## 人物关系初始矩阵

| 关系对 | 关系类型 | 初始状态 | 变化触发点 |
|--------|----------|----------|------------|
| A-B | 师徒/兄弟/敌对 | 当前关系状态 | 第N章：触发事件 |
```

**编写原则**:
- 控制在前 1500 字符内（LLM 截取限制）
- 核心人物至少 5-7 个，配角可在 `plot_graph.json` 的 `required_characters` 中临时添加
- 成长弧光要清晰可追踪
- 禁忌要明确（LLM 会严格遵守）

## 3. `bible/style_bible.md` — 文风规则

**作用**: 规定整部小说的文风标准。LLM 在生成任务卡时截取前 1000 字符。

**必须包含的部分**:

```markdown
## 叙事视角
[第三人称/第一人称/多视角切换规则]

## 语言风格
- **整体**：[整体语言基调]
- **对话**：[对话风格]
- **战斗描写**：[战斗场景写法]
- **心理描写**：[内心戏处理]
- **环境描写**：[环境描写的篇幅和使用方式]

## 情感基调范围
- 主基调：[整体情绪]
- 允许范围：[情绪波动的上下限]
- 禁止：[绝对不允许的情绪]

## 章节结构偏好
- 每章开头：[切入方式]
- 章末：[钩子要求]
- 场景切换：[分隔符]
- 单章字数目标：[数字]

## 禁忌
- [禁止项1]
- [禁止项2]
...
```

**编写原则**:
- 控制在 1000 字符以内
- 越具体越好（避免模糊描述如"优美"）
- 用列表形式，便于 LLM 逐项检查

## 4. `bible/author_intent.md` — 创作意图

**作用**: 按章节区间定义主题、情绪曲线、禁令。**这是最重要的文件之一**，直接影响每章的任务卡生成。

**必须包含的部分**:

```markdown
## 第一阶段：阶段名（第X-Y章）

- chapter_range: [起始章, 结束章]
  theme: "本阶段主题"
  emotion_curve:
    X: "情绪标签"        # 关键节点的情绪标记
    Y: "情绪标签"
  forbidden:
    - "绝对禁止的事件A"
    - "绝对禁止的事件B"
  note: "作者备注（可选，给LLM的额外提示）"

- chapter_range: [起始章, 结束章]
  theme: "下一阶段主题"
  ...
```

> **区间划分建议**:
> - 每个区间 50-200 章
> - 相邻区间之间不要重叠
> - 覆盖全部 3000 章

### 情绪标签库（推荐值）

| 标签 | 含义 |
|------|------|
| "压抑" | 低沉、困境、无力感 |
| "微光" | 希望初现、小转机 |
| "希望" | 积极向上、充满期待 |
| "振奋" | 高潮前的蓄力 |
| "危机" | 紧张、危险逼近 |
| "破茧" | 蜕变、突破 |
| "探索" | 好奇、未知 |
| "惊悚" | 恐惧、悬疑 |
| "蜕变" | 成长、成熟 |
| "开阔" | 视野打开、新发现 |
| "背叛" | 信任破裂 |
| "沉淀" | 反思、积累 |
| "疑惑" | 谜团浮现 |
| "震撼" | 重大揭露 |
| "决意" | 下定决心 |
| "沉重" | 悲壮、牺牲 |
| "抗争" | 不屈、战斗 |
| "终局" | 最终决战 |

### forbidden 项的写法

```yaml
forbidden:
  - "主角突破到XX境界"      # 境界禁令
  - "XX角色正式出场"        # 出场禁令
  - "揭露XX秘密"            # 信息禁令
  - "XX与YY产生感情线"      # 关系禁令
```

**编写原则**:
- 每个区间的 `forbidden` 要具体到事件级别，不要笼统
- `emotion_curve` 标注该区间内关键章节的情绪走向
- `note` 中记录重要的剧情转折点（供 LLM 参考但不强制执行）

## 5. `bible/ending_bible.md` — 终局设定

**作用**: 定义不可更改的结局和关键伏笔回收计划。LLM 在最后 50 章会严格遵循此文件。

**必须包含的部分**:

```markdown
## 不可更改的结局
- [主角的最终成就]
- [配角的最终命运]
- [世界的最终状态]

## 人物最终命运锚点
| 人物 | 最终命运 | 不可违背 |
|------|----------|----------|
| 姓名 | 结局描述 | 绝对规则 |

## 关键伏笔必须回收
1. F001：[伏笔名称] = [真相]（第N章揭示）
2. F002：[伏笔名称] = [真相]（第N章首次激活）
...

## 主题
"[一句话概括全书主题]"
```

**编写原则**:
- 结局要具体但不过度细节化（留 LLM 发挥空间）
- "不可违背"列是硬约束，违反会导致 review fail
- 伏笔编号与 `foreshadow/registry.json` 中的 ID 对应
- 主题要一句话能说清，用于最后阶段的 tone 校验

## 6. `planning/volumes.json` — 卷纲

**作用**: 将 3000 章划分为若干卷，每卷有独立的主题和高潮。LLM 通过 `volumes.volumes[]` 数组读取。

**JSON 结构**:

```json
{
  "volumes": [
    {
      "id": "V01",
      "title": "卷名",
      "chapter_range": [起始章, 结束章],
      "theme": "本卷主题",
      "core_conflicts": [
        "冲突1描述",
        "冲突2描述",
        "冲突3描述"
      ],
      "climax_chapter": 100,
      "climax_description": "本卷高潮章的具体描述"
    }
  ]
}
```

**字段说明**:

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | V01, V02, ... 用于 `plot_graph.json` 引用 |
| `title` | ✅ | 卷名，4-8字为宜 |
| `chapter_range` | ✅ | [起始章, 结束章]，闭区间 |
| `theme` | ✅ | 一句话概括本卷主题 |
| `core_conflicts` | ✅ | 3-5个核心冲突，每个一句话 |
| `climax_chapter` | ✅ | 本卷高潮章号 |
| `climax_description` | ✅ | 高潮章的具体事件描述 |

**编写原则**:
- 每卷 100-400 章，共 8-12 卷
- `core_conflicts` 中的冲突要在本卷内展开并部分解决
- `climax_description` 要具体到事件级别（如"韩玄击败内门弟子"），不要抽象
- 卷与卷之间的主题要有递进关系（从小到大地展开世界观）

## 7. `planning/plot_graph.json` — 剧情DAG

**作用**: 定义剧情节点之间的依赖关系。每个节点代表一个关键剧情事件，关联到特定章节范围和角色。

**JSON 结构**:

```json
{
  "nodes": [
    {
      "id": "N001",
      "type": "main_plot",
      "volume": "V01",
      "chapter_target": 1,
      "description": "剧情事件的详细描述",
      "depends_on": ["N000"],
      "required_characters": ["C001"],
      "emotional_tone": "情绪描述",
      "foreshadow_links": ["F001"]
    }
  ],
  "edges": [
    { "from": "N001", "to": "N002", "type": "dependency" }
  ]
}
```

**节点类型 (`type`)**:

| 类型 | 说明 |
|------|------|
| `"main_plot"` | 主线剧情节点（必须完成） |
| `"side_plot"` | 支线剧情节点（可选填充） |
| `"foreshadow"` | 伏笔埋设节点 |
| `"character_development"` | 角色成长节点 |
| `"world_expansion"` | 世界观扩展节点 |

**字段说明**:

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | N001, N002, ... 全局唯一 |
| `type` | ✅ | 节点类型（见上表） |
| `volume` | ✅ | 所属卷 ID（引用 `volumes.json`） |
| `chapter_target` | ⚠️ | 目标章节号（LLM 搜索前后20章的相关节点） |
| `description` | ✅ | 剧情事件的具体描述，1-3句话 |
| `depends_on` | ✅ | 前置依赖节点 ID 列表 |
| `required_characters` | ✅ | 本章必须出现的角色 ID 列表 |
| `emotional_tone` | ✅ | 情绪基调，如"压抑→希望" |
| `foreshadow_links` | ⚠️ | 关联的伏笔 ID 列表 |

**边 (`edges`)**:
- 可选。如果 `depends_on` 已经表达了依赖关系，edges 可以省略
- 主要用于表达非依赖关系的连接（如并行线索）

**编写原则**:
- 前 100 章至少 12-15 个节点（LLM 搜索窗口 20 章）
- 后续章节可以稀疏一些，每 50-100 章 5-8 个节点
- `chapter_target` 不必精确到某章，给 LLM 灵活性
- `description` 要具体到事件级别，不要抽象主题
- 保持 DAG 无环（`depends_on` 只能指向 ID 更小的节点）

## 8. `simulation/rules.json` — 世界运行规则

**作用**: 定义修炼速度、势力扩张、资源分布等量化规则。LLM 通过 `WorldSimulator` 读取，用于计算世界状态。

**JSON 结构**:

```json
{
  "realm_progression": {
    "description": "各境界突破所需平均章节数",
    "base_rates": {
      "境界名": { "min_chapters": 30, "max_chapters": 80, "average": 50 }
    },
    "modifiers": {
      "天材地宝": 0.7,
      "顿悟": 0.5
    }
  },
  "faction_expansion": {
    "description": "势力扩张速率规则",
    "base_growth_per_100_chapters": {
      "势力名": 1.0
    },
    "conflict_chance_per_chapter": 0.05
  },
  "resource_distribution": {
    "description": "资源分布密度",
    "rare_item_per_chapters": 20,
    "common_item_per_chapters": 5
  },
  "power_scaling": {
    "description": "战力平衡规则",
    "realm_gap_multiplier": 3.0,
    "same_realm_variance": 0.3
  }
}
```

**编写原则**:
- 通常不需要修改，使用默认值即可
- 如果想调整修炼节奏，修改 `realm_progression.base_rates` 中的 `average`
- `conflict_chance_per_chapter` 影响随机事件频率

## 9. `simulation/constraints.json` — 角色约束

**作用**: 定义角色的境界锁定和剧情锁定。LLM 在生成任务卡时通过 `WorldSimulator.get_constraints_summary()` 读取。

**JSON 结构**:

```json
{
  "C001": {
    "name": "角色名",
    "realm_lock": {
      "current": "当前境界",
      "locked_until_chapter": 50,
      "reason": "锁定原因说明"
    }
  },
  "C004": {
    "name": "柳如烟",
    "plot_lock": {
      "first_appearance_chapter": 200,
      "identity_reveal_chapter": 600,
      "reason": "为什么这个时间点出场/揭露"
    }
  }
}
```

**两种锁定类型**:

### realm_lock（境界锁定）
```json
"realm_lock": {
  "current": "炼气期三层",
  "locked_until_chapter": 50,
  "reason": "原因说明"
}
```

### plot_lock（剧情锁定）
```json
"plot_lock": {
  "first_appearance_chapter": 200,
  "identity_reveal_chapter": 600,
  "reason": "原因说明"
}
```

**编写原则**:
- 每个主要角色都应该有 `realm_lock`（至少写当前境界和解锁章节）
- `plot_lock` 用于控制角色首次出场、身份揭露等关键事件的时间点
- `reason` 字段很重要——LLM 会将其放入 prompt 中作为约束理由

## 10. `foreshadow/registry.json` — 伏笔注册表

**作用**: 管理所有伏笔的埋设和回收计划。LLM 在生成任务卡时会筛选出 `plant_chapter <= current <= resolve_chapter` 的活跃伏笔。

**JSON 结构**:

```json
{
  "foreshadows": [
    {
      "id": "F001",
      "plant_chapter": 3,
      "plant_context": "伏笔埋设的背景描述",
      "clue_plan": [
        {"chapter": 20, "intensity": "隐晦提示", "method": "具体写作手法"},
        {"chapter": 100, "intensity": "明显异样", "method": "具体写作手法"}
      ],
      "resolve_chapter": 2800,
      "resolve_method": "伏笔回收的方式描述",
      "importance": 0.98,
      "status": "planned",
      "linked_node": "N003"
    }
  ]
}
```

**字段说明**:

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | F001, F002, ... 全局唯一，需与 `ending_bible.md` 对应 |
| `plant_chapter` | ✅ | 伏笔开始埋设的章节 |
| `plant_context` | ✅ | 埋设伏笔时的背景/情境 |
| `clue_plan` | ✅ | 分阶段的暗示计划（见下） |
| `resolve_chapter` | ✅ | 伏笔回收的目标章节 |
| `resolve_method` | ✅ | 回收方式的描述 |
| `importance` | ✅ | 重要性 0-1，越高越不能遗漏 |
| `status` | ⚠️ | `planned` / `active` / `resolved` / `abandoned` |
| `linked_node` | ⚠️ | 关联的 plot_graph 节点 ID |

### clue_plan 阶段强度

| 强度值 | 说明 | 适用阶段 |
|--------|------|----------|
| `"隐晦提示"` | 几乎不明显，重读者能发现 | 埋设初期 |
| `"明显异样"` | 读者会注意到但不确定含义 | 中期铺垫 |
| `"接近揭露前兆"` | 读者开始怀疑真相 | 回收前夕 |
| `"关键道具"` | 直接展示关键物品/信息 | 首次接触 |
| `"惊悚揭示"` | 突然揭露令人震惊 | 高潮揭示 |

**编写原则**:
- 每个伏笔至少 3 个 `clue_plan` 阶段
- `importance >= 0.7` 的伏笔必须在 `ending_bible.md` 中对应回收
- 伏笔数量建议 10-30 个，太多会分散注意力
- `status` 可在生产运行时由 pipeline 自动更新

## 11. `memory/world_state/characters.json` — 角色状态

**作用**: 记录每个角色的实时状态（境界、伤势、人际关系等）。**通常由 pipeline 自动生成，不需要手动编辑。**

**JSON 结构**（自动生成）:

```json
{
  "C001": {
    "name": "韩玄",
    "realm": "炼气期三层",
```

## 常见问题

### Q: bible 文件写多少字合适？

A: 每个文件都有字符截断限制：
- `world_bible.md`: 2000 字符（前 2000 字会被发送给 LLM）
- `character_bible.md`: 1500 字符
- `style_bible.md`: 1000 字符
- `author_intent.md`: 2000 字符
- `ending_bible.md`: 无截断（全文发送）

**建议**: 把最重要的信息放在前面，次要信息放后面。

### Q: 生产过程中能修改 bible 文件吗？

A: **不建议**。bible 文件在 `ChapterDirector.__init__()` 时一次性加载到内存缓存中。修改后需要重启 pipeline 才能生效。如果确实需要修改，先停止 pipeline → 修改文件 → 重新启动。

### Q: plot_graph.json 必须写满 3000 章吗？

A: 不需要。LLM 只会搜索 `chapter_target` 在当前章 ±20 范围内的节点。所以只需要提前写好未来 20-40 章的节点即可。后续节点可以在生产过程中逐步补充。

### Q: 伏笔可以中途新增吗？

A: 可以。在 `foreshadow/registry.json` 中追加新的伏笔条目即可。LLM 会在每章生成时重新扫描注册表。

### Q: 如何知道 bible 文件是否写够了？

A: 跑一个 5 章的 mini test。如果 review 频繁出现"世界观不一致"或"人物OOC"，说明 bible 文件不够详细。如果 review 分数普遍 80+，说明 bible 内容充足。
