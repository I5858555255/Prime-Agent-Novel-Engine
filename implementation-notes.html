Decouple TUI Implementation Notes

This file tracks implementation choices while moving interactive mode toward consuming a daemon-compatible agent connection boundary.

Design Decisions

  • The first boundary is named AgentConnection. It is intentionally client-oriented: methods describe what the UI wants to do, not how AgentSession performs the work. That keeps the TUI from depending on runtime/session ownership details.
  • The connection surface is modeled around the daemon protocol instead of JSON-RPC mode. JSON-RPC already proved that command transport works, but daemon mode is the control plane we need local interactive mode to consume.
  • Bash execution is excluded from the connection surface and no longer starts from interactive mode. The requested path treats IPython as the only tool that matters for this migration, so bash-specific session commands should not hold up daemon-first decoupling.
  • Runtime rebinding is owned by the connection adapter. In the old architecture, InteractiveMode registered callbacks directly on AgentSessionRuntime. In the new architecture, the TUI should subscribe to AgentConnection replacement events and use a before-invalidate hook exposed by the connection.
  • DaemonAgentConnection.onBeforeSessionInvalidate() is currently a no-op. A remote client cannot synchronously clean up server-owned extension/runtime state before the daemon swaps sessions; it should react to session_replaced after the daemon rebinds.
  • Daemon extension UI requests now carry request IDs and can be answered through extension_ui_response. Fire-and-forget UI updates still broadcast as requests, but dialogs wait for a response, timeout, abort signal, or session close. If no client is attached, dialogs return their fallback immediately so daemon-side work does not hang headlessly.
  • InteractiveMode now handles extension_ui_request connection events by validating JSON payloads at the TUI boundary, rendering local TUI dialogs for select, confirm, input, and editor, and replying through the connection. Non-dialog UI requests mutate local status/widget/title/editor state without an acknowledgement.
  • The line-oriented daemon attach client cancels dialog-style extension UI requests. That client cannot render rich TUI dialogs, so explicit cancellation is safer than leaving daemon extension code waiting.
  • Queued steering and follow-up messages are now part of AgentConnection via getQueue() and clearQueue(). The TUI keeps a small local queue snapshot updated from queue_update events so rendering stays synchronous while the queue itself remains core-owned.
  • Slash command discovery for autocomplete and streaming/compaction routing now comes from AgentConnection.getCommands(). In-process mode still attaches local extension argument completers when available; daemon-backed clients will get command names/descriptions without executable completion callbacks.
  • InteractiveMode now requires an injected AgentConnection. Local fallback behavior is preserved by wiring InProcessAgentConnection in main.ts, not by giving the TUI a runtime-owning constructor.
  • Normal interactive mode now starts or reuses the local daemon, creates a daemon-owned session, attaches a DaemonAgentConnection, and injects that connection into InteractiveMode. The client prepares local service objects for settings/auth/themes/model browsing, but it does not construct a local AgentSessionRuntime for normal daemon-backed startup.
  • The daemon-vs-in-process interactive routing decision is now captured in shouldUseDaemonInteractive(). Normal interactive startup chooses the daemon-backed path; the explicit in-process exceptions are PI_STARTUP_BENCHMARK, --no-session, --help, and --list-models.
  • --no-session and PI_STARTUP_BENCHMARK remain in-process for now. The daemon protocol does not yet represent an in-memory no-session interactive session, and the startup benchmark should continue measuring TUI startup without daemon process startup.
  • When InteractiveMode is backed by an injected connection, it no longer binds local runtime extensions or local extension shortcuts. Extension command execution and lifecycle hooks belong to the daemon runtime; the TUI only handles daemon-originated UI requests and local chrome.
  • InteractiveMode now treats AgentConnectionState as the live execution-state cache for streaming, compaction, retry, goal, context, model, and scoped-model decisions. Full snapshots come from getState(); incremental updates are applied from session events.
  • Scoped model mutation is now a connection command (setScopedModels() / set_scoped_models) because model scope changes future agent execution. The selector remains a local UI/auth-model-registry flow, but the mutation is daemon-owned.
  • Session model availability now comes from AgentConnection.getAvailableModels(). The TUI still uses the local ModelRegistry for credential setup, provider display, persisted default-model settings, and auth warnings, but model candidates for the active session are now sourced from the execution owner.
  • Scoped-model selector state is now resolved from the connection-provided model candidates. Persisted settings patterns are interpreted against AgentConnection.getAvailableModels(), and session scoped-model mutations map selected provider/model IDs back to that same candidate set instead of asking the local ModelRegistry to recompute availability.
  • ModelSelectorComponent now treats injected availableModels as authoritative when refreshing the scoped-model tab. It can still use ModelRegistry for local models.json errors and fallback loading, but it no longer replaces daemon-provided scoped model objects with client-local registry objects when a connection model list was supplied.
  • Model selection persistence moved out of ModelSelectorComponent. The selector now emits the selected model as UI intent; InteractiveMode calls AgentConnection.setModel() and only writes the local default-model setting after the connection accepts the execution change.
  • Tool-definition lookup is now connection-backed in InteractiveMode. The TUI preloads definitions from AgentConnection.getToolDefinition() before rendering historical tool calls, and loads them as live tool events arrive. Rendering still uses a synchronous local cache because the TUI component tree expects synchronous constructors.
  • AgentConnection.getToolDefinition() now returns AgentConnectionToolDefinition, a serializable metadata DTO. It intentionally excludes execute, prepareArguments, renderCall, and renderResult callbacks from core ToolDefinition. In-process local extension render callbacks are exposed separately through InteractiveModeLocalSessionHost.getToolRendererDefinition(), so they remain local UI behavior instead of daemon/gateway protocol data.
  • Local UI dependencies are now grouped under InteractiveModeUiServices. This makes the distinction explicit: settings, auth/model registry, resource loading, themes, and local extension UI helpers are UI services, while prompts, model changes, queues, compaction, and session execution are connection operations.
  • Local extension binding and local withSession callbacks now sit behind InteractiveModeLocalSessionHost. This host is deliberately narrower than AgentSessionRuntime: it can bind local extensions, refresh local UI services after an in-process session replacement, and run the callback-bearing session replacement methods that are not transportable yet.
  • The in-process UI-service and local-session-host adapters now live in interactive-mode-services.ts, not in interactive-mode.ts. The TUI class consumes InteractiveModeUiServices, InteractiveModeLocalSessionHost, and AgentConnection abstractions; the adapter file is the compatibility layer that knows about AgentSessionRuntime.
  • FooterComponent no longer accepts or stores AgentSession. The current prime footer renders no session telemetry, so keeping a session reference there only preserved a stale coupling to core execution.
  • In daemon-backed interactive startup, main.ts now creates InteractiveModeUiServices from AgentSessionServices rather than creating a local AgentSessionRuntime. The TUI receives the daemon connection plus UI-local settings/auth/model/resource services, not a local session host or local execution runtime.
  • createInteractiveModeUiServicesFromServices() adapts service-only objects into the UI service interface. It uses local services for settings, themes, resource metadata, and model browsing, while execution state comes from AgentConnection.getState() and the TUI's connection-state cache.
  • InteractiveModeUiServices no longer exposes the live ResourceLoader. The TUI asks the UI-services adapter for registered themes through getThemes(); execution resource metadata comes from AgentConnection.getResourceSnapshot().
  • InteractiveModeUiServices also no longer exposes SessionManager. The TUI receives only initial cwd/session-name fallbacks for the short window before the first connection snapshot arrives. The full session manager is now reachable only through InteractiveModeLocalSessionHost for in-process local extension shortcut contexts.
  • InteractiveModeUiServices no longer exposes ExtensionRunner, system prompts, or abort signals either. Those are only needed when local in-process extension shortcuts are bound, so they now live on InteractiveModeLocalSessionHost. Daemon-backed interactive mode no longer constructs a client-side extension runner.
  • Waiting for the agent to become idle is now an AgentConnection operation (waitForIdle() / wait_for_idle) instead of a direct session.agent.waitForIdle() call from interactive mode.
  • Saved-session registry operations used by the interactive resume picker now go through AgentConnection: listSavedSessions(), renameSavedSession(), and deleteSavedSession(). The daemon protocol exposes these as separate saved-session commands rather than changing the existing live-session list / rename CLI surface.
  • Saved-session list rows now use connection-owned DTOs (AgentConnectionSavedSessionInfo and AgentConnectionSessionListProgress). The resume picker and search helper no longer import SessionInfo from SessionManager; adapters translate core session-manager data into the connection shape.
  • Daemon saved-session wire rows now also use the connection-owned AgentConnectionSavedSessionState type for lifecycle status. daemon-protocol.ts no longer imports SessionState from SessionManager. The daemon session-list summary status union also uses AgentConnectionSavedSessionStateStatus for inactive saved-session statuses.
  • Session tree rows now also use a connection-owned node shape, AgentConnectionSessionTreeNode, whose entry payload is an AgentConnectionSessionEntry union. TreeSelectorComponent and InteractiveMode no longer import SessionTreeNode or SessionEntry from SessionManager; adapters expose tree snapshots through AgentConnection.getSessionTree().
  • Session context snapshots now use AgentConnectionSessionContext. InteractiveMode.renderSessionContext() no longer imports SessionContext from SessionManager; both daemon and in-process adapters expose the context through AgentConnection.getSessionContext().
  • Resource listings and resource diagnostics now flow through AgentConnection.getResourceSnapshot(). The snapshot carries transport-safe metadata for context files, skills, prompt templates, extensions, themes, and diagnostics. It intentionally excludes resource contents, extension handlers, tool implementations, and the live ResourceLoader object. The loaded-resource display no longer falls back to the local resource loader for these execution-owned resources.
  • Resource origin and diagnostic metadata now use connection-owned DTOs: AgentConnectionSourceInfo, AgentConnectionResourceCollision, and AgentConnectionResourceDiagnostic. Core loaders still produce structurally compatible values, but the TUI, daemon protocol, and JSON-RPC command metadata no longer import the core source-info or resource-loader modules to describe data that crosses a client boundary.
  • Prompt-template listing is no longer part of InteractiveModeUiServices. Prompt metadata is displayed from AgentConnection.getResourceSnapshot(), and prompt slash commands come from AgentConnection.getCommands(), so the service method became a stale in-process assumption.
  • Extension slash command snapshots now include both the invokable command name and the originally registered extension command name. That lets daemon-backed clients keep the existing built-in-command conflict warning behavior even when the runner renames duplicate extension commands.
  • Session events now have a client-owned type, AgentConnectionSessionEvent. The shape currently mirrors the core session events that the TUI already renders, but interactive mode and daemon protocol no longer import or expose AgentSessionEvent directly. This makes event naming part of the connection contract instead of the live session object contract.
  • RLM child-agent snapshot types used by the TUI now also live under the connection namespace. The payloads are unchanged, but the TUI consumes them as daemon/client data instead of importing child-agent types from AgentSession.
  • Skill-block parsing moved from agent-session.ts to core/skill-blocks.ts. The TUI only needs a pure message-display parser there, not the session execution module. agent-session.ts still re-exports the parser so existing package consumers are not forced through a migration in this slice.
  • SessionStats moved to core/session-stats.ts. Connection, daemon, and RPC protocol types now import the stats DTO from a focused data module instead of from AgentSession. agent-session.ts still re-exports it for compatibility.
  • SessionImportFileNotFoundError moved to core/session-import-errors.ts. The daemon error serializer, interactive import handling, and tests now import the recoverable error from that focused module instead of from agent-session-runtime.ts. The runtime module still re-exports it while it remains the code path that throws it.
  • DaemonModeOptions moved from daemon-protocol.ts to daemon-mode.ts. The daemon protocol module now describes socket commands, responses, outbound messages, and protocol error metadata; the runtime factory used to construct daemon-owned sessions is a process-local daemon-mode concern.
  • Recoverable daemon command errors now carry optional errorInfo metadata. The local daemon connection rehydrates MissingSessionCwdError and SessionImportFileNotFoundError so existing interactive recovery flows still work when the runtime is daemon-owned.
  • Daemon-owned extension command callbacks are allowed to use setup and withSession because the extension command executes inside the daemon process. Those executable closures are never serialized through the daemon protocol; the daemon binding passes them directly to AgentSessionRuntime and broadcasts session_replaced after rebinding.
  • The daemon adapter normalizes serialized saved-session dates back to Date objects before the selector receives them. That preserves the selector's existing search, sorting, and age-rendering behavior while keeping JSON serialization inside the transport adapter.
  • Connection-backed saved-session listing uses the active session's session root for both current-folder and all-session scopes. That keeps daemon-backed TUI behavior tied to the daemon-owned runtime configuration instead of the client process defaults.
  • SessionSelectorComponent now accepts an optional delete callback. Interactive mode supplies the connection-backed deleter; the non-daemon --resume picker keeps the local fallback.

Deviations

  • get_state in the daemon protocol remains the existing lightweight session summary command. The richer TUI/client snapshot uses a new get_connection_state command instead of changing existing daemon CLI semantics.
  • InteractiveMode still has a local-only host for extension binding and callback-bearing withSession flows. That host is now defined in the adapter module rather than the TUI module, but it is still transitional because those callbacks are not daemon protocol concepts.
  • The daemon-backed TUI still performs local service preparation for settings, auth, model registry, resource loading, themes, CLI diagnostics, and initial message image resizing. It no longer constructs a local AgentSessionRuntime for normal interactive startup.
  • The service-backed daemon TUI adapter does not bind local extensions, but it still loads client-side resources for local UI needs such as themes and model browsing. Loaded-resource listings and execution resource diagnostics now use the daemon-owned resource snapshot instead of the client-side loader.
  • Bash commands are now explicitly rejected in interactive mode. Bash was intentionally left out of the requested connection surface, and keeping an in-process-only execution path would preserve a TUI-owned escape hatch into AgentSession.
  • /debug now fails with a user-visible error if the connection cannot return messages instead of falling back to local UI-service messages. That intentionally removes a stale in-process transcript fallback from daemon-backed mode.
  • Startup changelog gating now lets connection-state failures abort startup instead of falling back to a local message count. A daemon-backed TUI without connection state is not healthy enough to make accurate restored-session decisions.
  • Session browsing still uses local SessionManager.list(), local file deletion, and local rename writes only for non-daemon picker usages that do not construct an AgentConnection. Interactive mode now routes list, rename, and delete through the connection.
  • Daemon-backed custom tool render callbacks are not transported. Built-in tool rendering remains client-local, and custom daemon-side tools render from serializable metadata and results unless we later add a declarative renderer protocol.

Tradeoffs

  • I am starting with an in-process adapter and daemon protocol expansion before doing the full interactive-mode migration. This gives us compileable, testable seams and exposes daemon gaps early, instead of burying protocol work inside a large TUI edit.
  • Connection state is a snapshot, while session events remain incremental. A daemon client can always recover from missed events by asking for a fresh snapshot, and the in-process adapter can preserve the current event timing.
  • Extension command contexts can pass setup and withSession callbacks today. For daemon-loaded extensions, those closures stay daemon-side and can keep using AgentSessionRuntime directly through the daemon binding. For client-originated operations, I did not try to serialize closures over JSON; future transports need declarative replacement operations instead.
  • Text daemon attach now auto-cancels dialog UI requests. This prevents hangs for non-TUI clients, but a future multi-client daemon should advertise client capabilities so one non-interactive observer cannot cancel a dialog intended for an interactive UI client.
  • I kept autocomplete rendering synchronous by caching connection command/model/queue snapshots. The alternative was making editor completion providers async, which would have touched more of the TUI package and increased risk for this migration slice.
  • I chose to launch the daemon from normal interactive mode rather than only adding a new daemon tui command. That makes local usage exercise the daemon protocol by default, which is the architectural goal, while preserving the existing line-oriented prime-agent daemon attach behavior for simple terminal clients.
  • I extracted the daemon interactive routing decision into a pure helper instead of testing the full main() startup path. The full path depends on terminal process state, sockets, runtime services, and daemon process launch. The helper test proves the policy; daemon adapter and binding tests cover the protocol behavior underneath.
  • I disabled local extension binding in daemon-backed mode instead of keeping both local and daemon extension hosts active. Running both would preserve some local extension UI affordances, but it risks duplicate lifecycle hooks, duplicate command handlers, and confusing ownership of extension state.
  • I moved session model availability to AgentConnection while leaving provider setup and credential storage local. This is a narrower split than a full remote auth service: the daemon owns what the active session can use, and the local TUI still owns the credential UX needed by today's terminal client.
  • I left ModelSelectorComponent with a ModelRegistry dependency for now instead of introducing a larger selector service. The component still needs local models.json diagnostics and fallback model loading for non-connection tests/usages. The important decoupling point is that injected connection candidates override the registry for execution-facing scoped model objects.
  • I moved default-model persistence to the parent after AgentConnection.setModel() succeeds. The alternative was keeping persistence inside the selector for historical behavior, but that lets a rejected daemon command still mutate local settings. The new ordering makes the local setting a consequence of a successful execution-state change.
  • I kept the scoped-model selector's existing exact-ID behavior for user edits. When a user changes the checkbox set, the session scope is rebuilt from selected provider/model IDs, so thinking-level suffixes are not preserved by that UI interaction. Preserving them would require a richer selector model and is separate from moving ownership to the connection boundary.
  • I kept an event-updated state cache in the TUI instead of making every keypress or render path await daemon state. That preserves current synchronous TUI ergonomics, but means new daemon events must update the cache when they add connection-visible state.
  • I cached tool definitions in the TUI instead of making ToolExecutionComponent accept an async loader. Async component construction would spread the transport concern through more TUI code; a cache keeps the boundary explicit and can be invalidated on session rebind or reload.
  • I split tool presentation into two layers. AgentConnectionToolDefinition carries metadata that can cross JSON, while InteractiveModeLocalSessionHost can provide local renderer callbacks for in-process extension rendering. Returning full ToolDefinition from the connection would preserve a convenient TypeScript shape, but it would lie about what daemon and hosted transports can actually carry.
  • I made /debug connection-authoritative instead of best-effort. The old fallback could produce a debug file with local/stale messages after a daemon connection failure; the new behavior is less forgiving but tells the truth about the failed boundary.
  • I removed local message counts from InteractiveModeUiServices for the same reason as debug transcripts: message history is execution state. The TUI can cache connection snapshots, but it should not have a second local source of truth.
  • I kept neutral execution defaults inside InteractiveMode for the small window before the first connection snapshot is loaded. This is less featureful than reading from the local in-process session during startup, but it keeps the ownership model simple: local UI services do not mirror agent execution state.
  • I kept initial cwd/session-name fallbacks in the UI-services adapter instead of making the constructor wait for AgentConnection.getState(). That lets the TUI build its footer and terminal title synchronously, while avoiding a broad SessionManager dependency in the TUI.
  • I removed the legacy new InteractiveMode(runtimeHost, options) constructor instead of keeping it as a compatibility path. The safer staged version is to keep the in-process adapter, but force callers to cross the same AgentConnection boundary as daemon-backed interactive mode.
  • I moved saved-session registry operations onto AgentConnection instead of creating a separate daemon control-plane client in this slice. That makes interactive mode consume daemon protocol for the resume picker now, while leaving room to split registry/admin operations into a separate service later.
  • I duplicated the saved-session list row shape in the connection layer instead of aliasing SessionInfo. The two shapes are currently structurally identical, but the explicit DTO keeps future daemon/gateway clients from inheriting every internal SessionManager type change.
  • I reused the connection saved-session state DTO in the daemon protocol instead of creating a separate daemon-only status union. Saved-session lifecycle status is already part of the client-facing connection contract, so a second identical daemon type would add indirection without making the boundary clearer. The daemon still imports SessionInfo where it is actually reading saved-session files; only the client-visible status vocabulary moved out of SessionManager.
  • I duplicated the small source/diagnostic DTO shapes in the connection layer instead of aliasing SourceInfo or ResourceDiagnostic from core. The duplicated shapes are intentionally boring, but that is the point: protocol data should be stable because the client contract says so, not because the current loader implementation happens to export the same TypeScript interfaces.
  • I duplicated the serialized session entry union in the connection layer instead of importing SessionEntry. The JSON payload is intentionally the same data the session file already stores, but the TypeScript dependency now points at AgentConnectionSessionEntry so client code is not coupled to SessionManager.
  • I duplicated the session context wrapper in the connection layer while still carrying AgentMessage[]. The wrapper mirrors SessionManager.buildSessionContext() today, but gives the TUI a connection-owned import path. Fully connection-owned message DTOs should be handled in the later transcript/event protocol pass rather than mixed into this cleanup.
  • I extracted the in-process adapter helpers instead of deleting the fallback path. Removing the fallback would be cleaner architecturally, but --no-session and startup benchmarking still need a local execution path until the daemon protocol has equivalent semantics.
  • I removed the footer's AgentSession argument rather than replacing it with a footer snapshot. The footer is intentionally empty today; if telemetry returns later, it should read from AgentConnectionState or a dedicated presentation snapshot, not from a core session object.
  • I represented loaded resources as a snapshot instead of trying to expose ResourceLoader over the transport. A loader has filesystem and process behavior; a snapshot has stable data that can cross an in-process adapter, local daemon socket, or future hosted gateway.
  • I kept extension shortcut diagnostics local to the TUI path that binds local extensions. Shortcut conflict detection depends on effective client keybindings, so the daemon should not compute it until the protocol has an explicit client-capabilities or keybinding snapshot.
  • I copied the client-visible session event union into the connection layer instead of aliasing AgentSessionEvent. Aliasing would be less code today, but it would keep the public client boundary tied to whatever event shape the core runtime happens to use internally.
  • I serialized only the recoverable error identities the TUI already branches on. A broader typed-error system would be more general, but it would add protocol surface before we know which failures should be recoverable in hosted clients.
  • I kept compatibility re-exports for SessionStats, parseSkillBlock, and SessionImportFileNotFoundError in their old modules. The migration goal here is to stop new TUI/connection code from importing execution modules for transport-safe data, not to force external API consumers through unrelated import churn in this PR.
  • I kept the daemon create command's config payload typed as AgentSessionRuntimeConfig for now. That payload is still part of the local daemon control surface. I only moved the non-wire runtime factory out of the protocol module in this pass.
  • I extracted the existing session file deletion behavior into a shared core helper instead of changing the semantics. The daemon-backed path still tries trash first and falls back to unlink, but that now happens in the daemon process.
  • I removed the live interactive bash shortcut instead of adding bash operations to AgentConnection. This is a deliberate narrowing: historical bashExecution messages still render, but new shell work should go through IPython rather than a TUI-owned session method.
  • Interactive startup no longer ensures rg for the removed shell shortcut. It still ensures fd because path autocomplete needs it.
  • I split runtime preparation from runtime construction in main.ts. Normal daemon-backed interactive mode now runs only the preparation half locally, then asks the daemon to construct the execution runtime. RPC, print, daemon server mode, --no-session, and startup benchmark still use local runtime construction because they are not daemon-backed TUI clients.
  • Daemon session summaries now include runtime diagnostics and model fallback messages. That keeps user-visible startup warnings owned by the daemon runtime once the client stops constructing its own execution runtime.

Open Questions

  • Session selectors can pass concrete session paths today. If daemon clients should also accept short saved-session selectors for switch_session, we should route that command through resolveDaemonSessionPath().
  • Should theme metadata remain in the execution resource snapshot long-term, or should themes become an explicitly local UI service only? The current implementation includes daemon theme metadata in the loaded resource listing while still registering/rendering themes from local TUI services.
  • Decide whether saved-session registry operations should remain on AgentConnection or move to a separate daemon control-plane service before the hosted gateway work. Interactive mode now uses the connection, but the boundary may want to split "agent execution" from "session administration" later.
  • Client-originated setup and withSession callbacks are not transportable. Daemon extension-owned callbacks are covered by the daemon binding, but future web/gateway clients need a declarative replacement-session customization model if they should customize a freshly switched or forked session.
  • Confirm whether removing the live interactive bash shortcut is the desired final product behavior. I kept historical bash-message rendering so old sessions remain readable, but new ! commands now show an unsupported warning.
  • Decide how daemon protocol should represent --no-session. Today that flag stays on the in-process path to preserve non-persistence behavior.
  • Future hosted clients need a product decision for auth/model setup. The terminal client still edits local credentials directly, while the daemon protocol now owns active-session model availability. A web/gateway client likely needs a separate credentials/control-plane flow rather than reusing the local ModelRegistry UI.
  • Decide whether scoped-model thinking levels should become first-class editable UI state. The current selector still preserves existing behavior: settings patterns can carry thinking-level suffixes, but editing the checkbox selection sends exact model IDs and drops per-model thinking overrides.
  • Decide when to introduce fully connection-owned transcript/message DTOs. Session context now has a connection-owned wrapper, but it still carries AgentMessage[] so this migration does not rewrite the renderer and event protocol in the same pass.
  • Decide whether hosted/daemon clients need declarative custom tool rendering. Today local in-process extensions can still provide renderer callbacks through the local session host, but daemon/gateway clients should not receive JavaScript functions. A future protocol could use renderer IDs, structured display schemas, or fully generic rendering from tool result content.
  • Add broader full-TUI smoke coverage for daemon-backed interactive mode.
